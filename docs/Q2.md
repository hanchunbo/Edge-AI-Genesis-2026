## 第一阶段：ONNX Runtime 推理引擎集成 (W14-W17)

### W14 🔴 ONNX Runtime C++ 基础与环境搭建

**学习目的**  
AI 部署工程师的核心能力之一是脱离 Python 舒适区，在 C++ 环境下直接调用推理引擎。本周目标是完成 ORT C++ SDK 的环境配置，并理解其核心对象生命周期。

**核心范围**
- ONNX Runtime (ORT) C++ API 架构：`Ort::Env`, `Ort::SessionOptions`, `Ort::Session`
- `Ort::MemoryInfo` 与设备内存管理
- 模型输入输出节点动态查询（名称、形状、数据类型）
- **Zero-Copy Input**: 结合 Q1 W6 的 `mmap` + `std::span`，直接从内存映射区域创建 `Ort::Value`
- **双环境并行搭建（本周优先级最高）**：
  - VPS（2GB RAM，无 GPU）：CPU ExecutionProvider，用于 CI 和功能验证
  - 本地笔记本（RTX 3060）：CUDA ExecutionProvider，用于 W16+ GPU 推理与 Profiling
  - 两套环境均跑通 Hello World（加载模型 + 打印 I/O 节点），差异（ORT 版本、CMake 配置、CUDA 路径）同步更新到 `README.md` 「开发环境」节

**实战作业**  
编写 `InferenceEngine` 类：
- 加载 MobileNetV2 或 ResNet18 ONNX 模型
- 实现 RAII 风格：构造时加载，析构时释放
- 支持动态查询输入输出节点信息并打印
- 实现输入 Tensor 的零拷贝创建

**成功指标**
- 程序能正确加载模型并打印节点信息（名称、维度）
- 使用 `std::span` 封装输入 buffer，通过 `Ort::Value::CreateTensor` 创建 Tensor 时无 `memcpy` 调用
- 能解释 ORT `Env` 为何应该全局唯一
- VPS（CPU EP）与本地（CUDA EP）均能独立跑通，README 中有明确的双环境配置说明

**产出物**:
- `02_Inference_Analysis/w14_ort_basics/inference_engine.hpp`
- `README.md`（更新「开发环境」节，记录双环境差异）

### W15 🔴 高效的前处理与后处理流水线

**学习目的**  
推理引擎只是"中间商"，真正的性能瓶颈往往在前后处理。本周将 Q1 手写的图像算子接入推理流水线，形成端到端链路。

**核心范围**
- NHWC 到 NCHW 的内存布局转换 (HWC -> CHW) — 必须手写，禁用 `cv::dnn::blobFromImage`
- Image Normalization (Mean/Std 归一化) 的 SIMD 优化实现
- 后处理解码：Classification Top-K、Detection NMS 的 C++ 实现
- **复用 Q1 成果**：将 W9/W10 的 `BGR2Gray`, `Resize`, `Letterbox` 模块接入

**实战作业**  
构建完整的 `Preprocess -> Infer -> Postprocess` 管线：
- 输入：原始 BGR 图像 (`cv::Mat`)
- 预处理：Resize (保持比例 + Letterbox) -> HWC2CHW -> Normalize
- 推理：调用 W14 封装的 `InferenceEngine`
- 后处理：Top-5 分类解码（使用 ImageNet label 文件）

**成功指标**
- 对 Imagenet 测试图片输出正确的 Top-5 分类结果
- 预处理代码无冗余 `cv::Mat` 拷贝（使用 `std::span` 直接操作内存）
- 对比 "OpenCV `cv::dnn::blobFromImage`" vs "手写 HWC2CHW" 的耗时，差距 < 20%

**产出物**: `02_Inference_Analysis/w15_pre_post/pipeline_demo.cpp`

- I/O Binding：将输出 Tensor 直接绑定到预分配内存，减少 Device -> Host 拷贝
- YOLOv8/v10 输出头解析 (boxes, scores, classes)

**实战作业**

- 压力测试：输出不同 Batch Size (1, 4, 8) 下的 Latency 和 Throughput 曲线

**成功指标**
- 在 COCO 验证集的一张图片上输出正确的检测框（与 Python ultralytics 结果一致）
- `NMS` 单帧耗时 < 1ms (在 1000 个候选框场景下)
- 能解释 `InterOpNumThreads` 和 `IntraOpNumThreads` 的区别及适用场景

**核心范围**

- **Perf** + Flame Graph (火焰图) 采集 CPU 热点

**实战作业**

- 生成 CPU Flame Graph，定位热点函数
- 使用 Roofline 分析判断模型是 Compute-bound 还是 Memory-bound

**成功指标**
- 产出一份完整的性能诊断报告 (Markdown/PDF)，包含 Timeline 截图和火焰图
- 能精确说出三个阶段各占用的毫秒数
- 能根据 Roofline 分析结果判断优化方向（算力/带宽）

**产出物**: `docs/benchmarks/w18_profiling_report.md`, `02_Inference_Analysis/w18_profiling/`

### W19 🟡 量化理论 (Quantization Theory)

**学习目的**  
模型量化是 AI 部署工程师的核心技能。本周关注理论基础，理解 FP32 -> Int8 背后的数学原理与精度损失来源。

**核心范围**
- 对称量化 vs 非对称量化 (公式推导)
- Calibration (校准) 策略: Min-Max, Entropy (KL 散度), Percentile
- 量化误差分析 (MSE, SNR)
- **Per-Channel** vs **Per-Tensor** 量化的适用场景

**实战作业**  
(使用 Python + NumPy 完成，为 W20 做铺垫)
- 手写一个简单的 `Quantizer` 类，实现：
  - `quantize(weights, scale, zero_point)` -> int8
  - `dequantize(int8_weights, scale, zero_point)` -> float32
- 对一组随机权重进行伪量化，计算并可视化量化前后的 Histogram
- 分析不同 Calibration 策略对误差的影响

**成功指标**
- 能手写对称/非对称量化的数学公式
- 可视化图表清晰展示量化误差分布
- 能解释为何 Depthwise Conv 层通常需要 Per-Channel 量化

**产出物**: `02_Inference_Analysis/w19_quantization_theory/quantizer.py`, `02_Inference_Analysis/w19_quantization_theory/analysis_report.ipynb`

### W20 🔴 ONNX Runtime Int8 量化实战 (PTQ)

**学习目的**  
将理论落地。使用 ORT 官方量化工具对 YOLO 模型进行 PTQ (Post-Training Quantization)，并在 C++ 引擎中加载验证。

**核心范围**
- ORT Quantization Tool (`onnxruntime.quantization`) 使用
- 校准数据集准备策略（代表性样本选择）
- 敏感层分析：识别无法量化的层
- **混合精度 (Mixed Precision)**：敏感层保持 FP16/FP32，其余 Int8

**实战作业**  
将 YOLOv8n 模型量化为 Int8：
- 准备 100 张 COCO 校准图片
- 使用 MinMax/Entropy 两种策略分别量化
- 在 C++ `YOLODetector` 中加载 Int8 模型并运行推理
- 记录量化前后的模型体积、推理速度、mAP 精度

**成功指标**
- 模型体积减小 > 60% (FP32 -> Int8)
- 推理速度提升 > 1.3x（挑战目标：> 1.5x）
- mAP 掉点 < 2%（挑战目标：< 1%）

**产出物**: `02_Inference_Analysis/w20_int8_quantization/`, `docs/benchmarks/w20_quantization_results.md`
