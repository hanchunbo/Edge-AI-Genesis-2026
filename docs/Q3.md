## 第一阶段：TensorRT C++ 深度优化 (W27-W30)

### W27 🔴 TensorRT Engine 构建与 FP16 推理

**学习目的**  
Q2 通过 ORT TRT EP 感受了加速收益，本周直接调用 TensorRT C++ API，
理解 Engine 序列化/反序列化与 FP16 精度模式的工程细节。

**核心范围**
- TensorRT 核心对象生命周期：`IBuilder` → `INetworkDefinition` → `ICudaEngine` → `IExecutionContext`
- ONNX 模型解析：`nvonnxparser::createParser`
- Engine 序列化与反序列化（`.trt` 文件，避免每次重建耗时）
- FP16 模式开启：`setFlag(BuilderFlag::kFP16)`，与 FP32 精度对比
- CUDA Stream 管理：`cudaStream_t` + 异步推理

**实战作业**  
将 YOLOv8n 部署到 TensorRT：
- 构建并序列化 FP32 / FP16 Engine
- 实现完整推理管线：Host → Device 拷贝 → `enqueueV3` → Device → Host 拷贝
- 与 Q2 W17 EP 对比数据（CPU EP / CUDA EP / TRT EP / TRT FP16）形成四路对比表

**成功指标**
- Engine 构建成功，序列化文件可复用（重启不重建）
- FP16 推理速度相比 FP32 提升 > 30%（RTX 3060 tensor core 加速）
- 检测结果与 ONNX Runtime CUDA EP 输出 IoU > 0.98（精度损失可控）

**产出物**:
- `03_Hardware_Acceleration/w27_tensorrt_fp16/trt_engine.hpp`
- `docs/benchmarks/w27_trt_vs_ort_comparison.md`

---

### W28 🔴 TensorRT INT8 量化与精度对齐

**学习目的**  
Q2 W20 用 ORT PTQ 做了 INT8 量化，本周直接在 TensorRT 内做 INT8 校准，
理解 TRT 的 Calibrator 接口与 Q2 ORT 量化工具的差异。

**核心范围**
- TRT INT8 Calibrator：`IInt8EntropyCalibrator2` 实现
- 校准数据集接口：`getBatchSize`, `getBatch`, `writeCalibrationCache`
- Layer-wise 精度调试：`setLayerPrecision` 做混合精度
- 精度对齐方法论：TRT 输出 vs PyTorch 输出逐层 MSE 比对

**实战作业**  
构建 YOLOv8n INT8 TRT Engine：
- 实现 `CocoCalibrator`，使用 100 张 COCO 校准图片
- 对比 FP32 / FP16 / INT8 三档：模型体积、推理延迟、mAP
- 与 Q2 W20 的 ORT INT8 结果横向对比，分析两种量化路径的精度/速度差异

**成功指标**
- INT8 Engine 推理延迟 < FP16 的 70%（挑战：< 50%）
- mAP 掉点 < 2%（与 FP32 基线相比）
- 校准缓存可序列化，相同模型不重复校准

**产出物**:
- `03_Hardware_Acceleration/w28_trt_int8/coco_calibrator.hpp`
- `docs/benchmarks/w28_quantization_ladder.md`（FP32/FP16/INT8 三阶梯对比）

### W29 🟡 CUDA Kernel 与 TRT Plugin 入门

**学习目的**  
当 TRT 不支持某个 ONNX 算子时，需要手写 CUDA Plugin 注册进去。
理解这个机制是从"调参工程师"到"推理引擎开发者"的分水岭。

**核心范围**
- CUDA 编程模型复习：Grid/Block/Thread，Shared Memory，Warp 级原语
- TRT Plugin 接口：`IPluginV3`，注册与序列化
- 自定义算子场景：以 `GELU` 激活函数为例（NLP 模型常见，TRT 早期版本不支持）
- `nsight-compute` 初探：分析 Kernel 的 SM 利用率和内存带宽占用

**实战作业**  
实现一个 `GeluPlugin`：
- 手写 CUDA Kernel：`gelu(x) = x * 0.5 * (1 + tanh(...))`
- 通过 `IPluginRegistry` 注册，在含 GELU 层的 BERT ONNX 中测试
- 用 `nsight-compute` 采集 Kernel Profile，分析优化空间

**成功指标**
- `GeluPlugin` 输出与 PyTorch 参考实现数值误差 < 1e-5
- Kernel Occupancy > 50%（说明 GPU 利用率合理）
- 能解释 Shared Memory 与 L1 Cache 的关系

**产出物**:
- `03_Hardware_Acceleration/w29_cuda_plugin/gelu_plugin.cu`
- `docs/benchmarks/w29_kernel_profile.md`

## 第二阶段：ARM 跨平台部署 (W31-W33)

### W31 🟡 ORT ARM ExecutionProvider 部署

**学习目的**  
边缘 AI 的终局场景在 ARM 设备（手机、手表、开发板），
用 ONNX Runtime 的 ARM EP 是成本最低的跨平台路径。

**核心范围**
- 树莓派 5 / Android (Termux) 环境搭建
- ORT ARM 预编译包获取与 CMake 集成

- 功耗 vs 延迟权衡：`OrtSessionOptions` 的线程配置

**实战作业**  
在 ARM 设备上运行 MobileNetV2 分类推理：
- 对比 ARM CPU EP + XNNPACK EP 的延迟
- 记录内存占用与功耗（用 `vcgencmd measure_temp` / `powertop`）
- 与 VPS x86 CPU EP 数据对比，量化"边缘 vs 云端"的 latency 差异

**成功指标**
- 在树莓派 5 上 MobileNetV2 单帧推理 < 50ms
- 功耗数据有记录（mW 级别）

**产出物**:

### W32 🟡 NCNN 部署——零依赖纯 ARM 推理

**学习目的**  
NCNN 是腾讯开源的纯 C++ 推理框架，无任何第三方依赖，
是 MCU / 嵌入式 Linux（无 Python 环境）场景的核心选型。

**核心范围**
- NCNN 模型转换：`onnx2ncnn` 工具链
- NCNN C++ API：`ncnn::Net`, `ncnn::Mat`, `ncnn::Extractor`
- NCNN ARM NEON 优化：Winograd 卷积、BF16 加速
- 与 ORT ARM EP 的对比：灵活性 vs 极限性能

**实战作业**  
将 YOLOv8n 转换并部署到 NCNN：
- `onnx2ncnn` 转换 + 手动处理不支持算子的替换
- 实现 NCNN 版 YOLO 推理管线
- 与 W31 ORT ARM 数据对比，量化 NCNN 的速度优势

**成功指标**
- 转换后 NCNN 模型检测结果与 ORT 版本一致（主要框 IoU > 0.95）
- NCNN 推理速度比 ORT ARM EP 快 > 20%

**产出物**:
- `03_Hardware_Acceleration/w32_ncnn/ncnn_yolo.cpp`
- `docs/benchmarks/w32_ncnn_vs_ort.md`

### W34 🔴 Docker 容器化 AI 推理服务

**学习目的**

**成功指标**
- 镜像体积 < 3GB（含 CUDA Runtime + ORT + 模型）
- 容器内推理延迟 vs 裸机推理延迟差异 < 5%（容器开销可忽略）

**产出物**:

### W35 🟡 gRPC 推理服务接口设计

**学习目的**  
把推理能力暴露为网络服务，是 AI 平台化的基础。
gRPC 的高性能和强类型是工业级推理服务的主流选择。

**核心范围**
- Protocol Buffers 定义推理请求/响应（`InferRequest`, `InferResponse`）
- gRPC C++ Server：异步服务端（`grpc::ServerBuilder`）
- 客户端 Python stub 生成与测试
- 连接池与负载均衡初探

**实战作业**  
为 YOLODetector 封装 gRPC 服务：
- 定义 `proto`：`DetectRequest {bytes image_data, int32 batch_size}` → `DetectResponse {repeated BBox boxes}`
- 服务端：C++ gRPC Server，内部调用 `YOLODetector::Detect`
- 客户端：Python 脚本发送图片，接收检测框并可视化
- 压力测试：100 并发请求下的 QPS 与 P99 延迟

**成功指标**
- 单客户端 QPS > 30（RTX 3060，batch=1）
- P99 延迟 < 3× P50（无严重尾延迟）

**产出物**:
- `04_System_Integration/w35_grpc/inference.proto`
- `04_System_Integration/w35_grpc/inference_server.cpp`
- `04_System_Integration/w35_grpc/client_test.py`

## W37-W39：Q3 综合项目

### 🟡 项目名称：**InferHub — 多后端推理调度器**

**任务描述**  
综合 Q3 所有技术，构建一个后端可插拔的推理调度服务。
这是证明"能做架构决策"而非"只能调 API"的核心项目。

**核心功能**
1. **多后端抽象层**：统一 `IInferBackend` 接口，底层可选 ORT-CPU / ORT-CUDA / TensorRT / NCNN
2. **运行时后端切换**：通过 gRPC 配置接口，在不重启服务的情况下切换后端
3. **自适应负载调度**：根据当前 GPU 利用率自动选择后端（GPU 负载 > 90% 时降级到 CPU）
4. **完整可观测性**：Prometheus metrics（QPS, P99 latency, GPU util）+ Grafana 看板

**考核标准**
- 后端切换延迟 < 2s（热切换，不断服）
- 代码覆盖率 > 75%（核心调度逻辑）
- Docker Compose 一键启动全套服务

**产出物**: `04_System_Integration/inferhub/`
